### M7
Question: Lag metric. Give the exact per-character lag definition the legacy producers compute, the
inputs a run must retain to compute it, and whether production replay exposes them today. Anchor on
`replay.py`'s `on_segment` hook and on the legacy producer that computes lag. State what the
evaluator must capture per update that a plain `replay_wav` call currently discards.
- answer: For each emitted update event, legacy `char_lags` sets `end=commit_audio_s`, `start=audio_from_s` or the previous committed endpoint, spreads the event's `len(text)` characters uniformly across that audio span at midpoint positions `at_i=start+(end-start)*(i+0.5)/len(text)`, and records `lag_i=emit_s-at_i`; summary is `statistics.median(sorted(lags))`, p90 index `int(0.9*n)`, and max. Required retained inputs are event `text`, `audio_from_s`, `commit_audio_s`, and timing `emit_s`; retain `buffer_end_s` and per-update decode seconds too so pipeline delay and the computational clock remain auditable. Production replay exposes only the final `on_segment(start,n,seg_len,decode_s,text)` per closed VAD segment/utterance; `_vac_segments.update` currently discards the processor's returned commit-audio endpoint (`commit, _`), while `finalize` reports only the whole utterance. Thus `replay_wav` cannot reconstruct intermediate character lag. Add an observation-only per-update hook to production `_vac_segments`/replay that records deterministic commit text/audio endpoints separately from measured decode duration; derive `emit_s` on replay's virtual audio clock as `now=max(now,buffer_end_s)+decode_s`. A final update uses the utterance end as `commit_audio_s`. Do not estimate lag from final `segments`, because that collapses every early VAC commit into one utterance-close event.
